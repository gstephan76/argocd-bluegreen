# OpenShift Argo CD Blue/Green Demo

This example demonstrates a simple **Blue/Green deployment pattern on Red Hat OpenShift** that can be managed by **Argo CD**.

The demo deploys two independent HTTP application versions:

- **app-v1** — BLUE
- **app-v2** — GREEN

Both versions can be tested independently through their own OpenShift Routes, while a stable production Route points to a dedicated production Service.

The production Service selects which version is live.

## Architecture

The two versions run at the same time.

```text
                         Production traffic
                                |
                                v
                           Route: app
                                |
                                v
                   Service: app-production
                                |
                         selector version=v1
                                |
                                v
                         app-v1 / BLUE
```

At the same time, each application version has its own test Route:

```text
Route: app-v1                        Route: app-v2
     |                                    |
     v                                    v
Service: app-v1                       Service: app-v2
     |                                    |
     v                                    v
app-v1 / BLUE                        app-v2 / GREEN
```

This allows GREEN to be fully deployed and tested before it receives production traffic.

## Application Versions

### BLUE — app-v1

The BLUE deployment uses:

```text
app=bluegreen-app
version=v1
```

The HTTP response identifies the version as:

```text
APP VERSION 1
BLUE deployment
```

### GREEN — app-v2

The GREEN deployment uses:

```text
app=bluegreen-app
version=v2
```

The HTTP response identifies the version as:

```text
APP VERSION 2
GREEN deployment
```

---

## Initial Production State

The production Service starts with the following selector:

```yaml
spec:
  selector:
    app: bluegreen-app
    version: v1
```

Therefore production initially points to BLUE:

```text
Route app
    |
    v
app-production
    |
    v
version=v1
    |
    v
app-v1 / BLUE
```

The OpenShift production Route does **not** need to change during a promotion.

Only the selector of `app-production` changes.

# Promote BLUE to GREEN

In a GitOps workflow, the switch must be made in Git.

Edit:

```text
bluegreen-demo/app-production-service.yaml
```

Change:

```yaml
spec:
  selector:
    app: bluegreen-app
    version: v1
```

to:

```yaml
spec:
  selector:
    app: bluegreen-app
    version: v2
```

The resulting topology is:

```text
BEFORE PROMOTION

Route app
    |
    v
app-production
    |
    v
version=v1
    |
    v
app-v1 / BLUE


AFTER PROMOTION

Route app
    |
    v
app-production
    |
    v
version=v2
    |
    v
app-v2 / GREEN
```

Commit the change:

```bash
git add bluegreen-demo/app-production-service.yaml

git diff --cached --check

git commit -m "Promote green application to production"
```

Push it to the Git repository used by Argo CD:

```bash
git push
```

If Argo CD automated synchronization is enabled, Argo CD detects the commit and updates the production Service.

If automated synchronization is disabled, synchronize the Application manually from the Argo CD UI or CLI.

After synchronization:

```bash
curl -k \
  "https://$(oc get route app \
    -n bluegreen-demo \
    -o jsonpath='{.spec.host}')"
```

Expected response:

```text
APP VERSION 2
GREEN deployment
```

---

# Roll Back GREEN to BLUE

Rollback is the reverse operation.

Edit:

```text
bluegreen-demo/app-production-service.yaml
```

Change:

```yaml
version: v2
```

back to:

```yaml
version: v1
```

Commit:

```bash
git add bluegreen-demo/app-production-service.yaml

git diff --cached --check

git commit -m "Rollback production to blue application"

git push
```

After Argo CD synchronizes the repository, production points back to BLUE.

Verify:

```bash
curl -k \
  "https://$(oc get route app \
    -n bluegreen-demo \
    -o jsonpath='{.spec.host}')"
```

Expected:

```text
APP VERSION 1
BLUE deployment
```

# Direct OpenShift Switch for Lab Testing

For a quick lab test without committing to Git, the production Service can be patched directly.

## Switch BLUE → GREEN

```bash
oc patch service app-production \
  -n bluegreen-demo \
  --type merge \
  -p '{
    "spec": {
      "selector": {
        "app": "bluegreen-app",
        "version": "v2"
      }
    }
  }'
```

Verify:

```bash
oc get service app-production \
  -n bluegreen-demo \
  -o jsonpath='{.spec.selector}{"\n"}'
```

Then:

```bash
curl -k \
  "https://$(oc get route app \
    -n bluegreen-demo \
    -o jsonpath='{.spec.host}')"
```

Expected:

```text
APP VERSION 2
GREEN deployment
```

## Switch GREEN → BLUE

```bash
oc patch service app-production \
  -n bluegreen-demo \
  --type merge \
  -p '{
    "spec": {
      "selector": {
        "app": "bluegreen-app",
        "version": "v1"
      }
    }
  }'
```

Expected production response:

```text
APP VERSION 1
BLUE deployment
```

> **Important:** when Argo CD manages this directory, a manual `oc patch` creates configuration drift. If Argo CD self-healing is enabled, Argo CD can automatically restore the selector defined in Git. For a real GitOps promotion, always change the manifest in Git.

# Argo CD Behavior

Argo CD treats Git as the desired state.

For example:

```text
Git
 |
 | app-production selector = version:v1
 v
Argo CD
 |
 v
OpenShift
 |
 v
BLUE
```

After the promotion commit:

```text
Git
 |
 | app-production selector = version:v2
 v
Argo CD
 |
 v
OpenShift
 |
 v
GREEN
```

The production Route remains unchanged throughout the switch.

This is useful because:

- the production hostname remains stable;
- TLS configuration remains stable;
- external DNS does not change;
- both versions can coexist;
- GREEN can be validated before promotion;
- rollback is only a Service selector change.

# Verify Which Version Is Active

Inspect the production Service selector:

```bash
oc get svc app-production \
  -n bluegreen-demo \
  -o jsonpath='{.spec.selector.version}{"\n"}'
```

Possible values:

```text
v1
```

or:

```text
v2
```

You can also inspect the endpoints selected by the production Service:

```bash
oc get endpoints app-production \
  -n bluegreen-demo \
  -o wide
```

And inspect the matching pods:

```bash
oc get pods \
  -n bluegreen-demo \
  -l app=bluegreen-app,version=v1 \
  -o wide
```

or:

```bash
oc get pods \
  -n bluegreen-demo \
  -l app=bluegreen-app,version=v2 \
  -o wide
```

# Recommended Promotion Flow

A safe promotion sequence is:

```text
1. Deploy BLUE and GREEN
        |
        v
2. Production remains on BLUE
        |
        v
3. Test GREEN through app-v2 Route
        |
        v
4. Run functional / integration tests
        |
        v
5. Change app-production selector in Git
        |
        v
6. Commit and push
        |
        v
7. Argo CD synchronizes
        |
        v
8. Production switches to GREEN
        |
        v
9. Monitor GREEN
        |
        +---- success ---> keep GREEN
        |
        +---- failure ---> commit selector back to v1
```

## Summary

The key part of this implementation is that the production Route is permanent:

```text
Route app
    |
    v
Service app-production
```

Promotion only changes the Service selector:

```text
BLUE:

version=v1
    |
    v
app-v1
```

to:

```text
GREEN:

version=v2
    |
    v
app-v2
```

With Argo CD, this selector change is committed to Git and synchronized declaratively, making promotion and rollback simple, auditable, and reproducible.
